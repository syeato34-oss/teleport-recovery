### Trailing-slash routing follow-up

The canonical remains `https://teleportrecovery.co.uk/recovery/birmingham`. `netlify/edge-functions/canonical-birmingham.js`, declared only for the two Birmingham variants in `netlify.toml`, returns a permanent HTTP 301 from the trailing-slash URL to this canonical while preserving the query string verbatim. The canonical URL falls through to the existing static HTML rewrite, so it cannot redirect back to itself. Home/legal/callback/unknown routes are outside the declaration, and non-navigation methods are passed through.

Fresh live HTTP and browser checks at the time of this fix returned HTTP 200 and the correct Birmingham heading/title for **both** variants, with the same application asset and slash-free canonical. The reported earlier 404 could not be reproduced, so its historical cause is not established. The verified configuration defect was the missing permanent slash redirect. React already normalises both variants, and `dist/recovery/birmingham/index.html` already exists; neither needed a page rebuild/redesign. The old local QA server served directory indexes for both variants without checking a redirect, which did not test canonical HTTP behaviour.

[Netlify's documented redirect normalisation](https://docs.netlify.com/manage/routing/redirects/redirect-options/#trailing-slash) makes ordinary slash-only redirect rules unsafe: they match the slash-free URL too and can loop. Enabling global Pretty URLs would change the deliberately unredirected callback POST endpoint. The small route-scoped Edge Function avoids both problems, using standard Request/Response APIs without dependencies. The local production QA server executes the same handler; regression tests check GET/HEAD 301s, encoded/repeated query parameters, no loop, direct navigation/refresh, raw HTML canonical/title and sitemap consistency. This tests handler behaviour locally, not Netlify's deployed Edge runtime.

The next approved deployment must include the repository's Netlify configuration and Edge Function through Netlify's build/deploy workflow; uploading only Vite's `dist` folder does not include the function. Verify the deployed 301/Location and final 200 afterwards. No deployment, cache purge or Google Ads change was performed by this routing fix.

Routing-fix verification passed: all 34 unit tests, TypeScript, ESLint, production build and the focused browser suite. Browser checks covered GET/HEAD redirects, query preservation, direct loads/refreshes, unchanged homepage content at five widths, legal navigation, canonical tags and sitemap. Generated application asset hashes were unchanged. Netlify CLI was not installed, and the deployed Edge runtime was not tested because deployment was explicitly excluded.
